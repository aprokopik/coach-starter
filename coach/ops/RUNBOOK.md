# Runbook: how the coach runs

Operations only. Coaching rules are in `coach/engine/RULES.md`; the athlete in `coach/athlete/`; live state in `coach/CURRENT-STATE.md`. The scheduled-task prompts that call these steps are `coach/ops/TASK-PROMPT-morning.md` and `coach/ops/TASK-PROMPT-weekly.md` (the morning text is pasted into its task; since Nov 5, 2026 the weekly task, like the monthly research scan, reads its file from the repo at each run, so a change to that file needs no task edit; the prompts stay short and point here).

Three stages, each with its own failure line, so a dashboard problem never blocks the check-in and a data problem is said plainly:

| Stage | Steps | If it fails |
|---|---|---|
| **Data** | get the record, dispatch a pull, wait, compute facts, score predictions | continue with the data on hand; one line in the check-in |
| **Coach** | read, decide, write the check-in and the record, push | a failed push is noted as "record not saved" |
| **Publish** | rebuild and upload the dashboard | one line in the check-in; the repo stays the record of truth |

## Data

1. **Record.** Attach `{{GITHUB_OWNER}}/{{REPO}}` (add_repo, access push) if that tool exists. Clone once: `git clone --depth 20 https://github.com/{{GITHUB_OWNER}}/{{REPO}} /home/claude/{{REPO}}`. If the directory exists, never reset or delete: `git fetch origin && git checkout -B coach-run origin/main`. Push with `git push origin HEAD:main`. If the repo cannot be reached, send one short message saying so and stop; never guess readiness without data. **Not saved yet** (Nov 9, 2026, after a tester's evening answers and a knee note were stuck in chat): in any session that cannot reach the repo, whatever the athlete reports (feel answers, pain, a session, a weigh-in) is never dropped. End each reply with a "Not saved yet" block, dated, in the athlete's own words, and the one fix: talk to the coach in Claude Code with the repository selected (the check-in's own session, or claude.ai/code), since a regular Claude chat cannot save; if that session still cannot reach it, reconnect at claude.ai/connect-github. No later run can read a chat, so never say the next run will record it; ask the athlete to paste the block into a Claude Code session on the repository (or the check-in's own session). As soon as the repo is reachable in that session, write the block to `coach/LOG.md` (and the matching CSV rows) before anything else, and say it was saved.

2. **Fresh pull.** [data-2] GitHub's four scheduled pulls (cron 10:23, 11:23, 16:23 and 23:23 UTC) all run but land 5 to 10 hours late (Oct 23 to Nov 3, 2026; still about 1 PM ET for the 6:23 AM one on Nov 6 to 12), so none arrives before the check-in; they stay as the backstop for a day when no Claude task runs. Dispatch one: GitHub tool `actions_run_trigger`, method `run_workflow`, owner `{{GITHUB_OWNER}}`, repo `{{REPO}}`, workflow_id `pull-garmin.yml`, ref `main`, inputs `{"extra_days_back": "0"}`. Note the dispatch time. It takes 1 to 2 minutes; read (Coach step 1) meanwhile.
3. **Wait.** [data-3] One bash loop: `git fetch origin`, check whether `origin/main` has a "Garmin pull" commit newer than the dispatch time, every 30 s for up to about 4 minutes, then `git pull --ff-only origin main`. **Second try** (6.27.1, the athlete chose it Nov 12, 2026; data_paths `garmin` fallback): if nothing landed, check that no pull is running (`actions_list` method `list_workflow_runs`, workflow_id `pull-garmin.yml`, status `in_progress` or `queued`), dispatch once more exactly as in step 2 unless one is, and wait the same way up to about 4 more minutes. Only then, if still nothing landed, continue with the data on hand and say so in the check-in's data line.
4. **Feel answers, check-ins and lifts.** [data-4] First the check-in settings: "Check-in settings" step 1 with id `morning` (off: stop there), then its step 2. ArtifactData `list` of `feel_daily`, `feel_sessions`, `checkin`, `lift_log` and `lift_tap` on the dashboard (`coach/DASHBOARD.md`, "What the athlete enters"). Copy each new `lift_tap` document into `coach/lift_taps.csv` (date = the document id, for_date, answer yes or no, saved_at; a newer document for the same date replaces its row), the "Lifted yesterday?" tap that tells a skipped lift from an unlogged one. Copy new or newer documents into `coach/feel_daily.csv` and `coach/feel_sessions.csv` as Reported (scale column; `manual-` ids; the `footing` field into the footing column and the `ground` field into the ground column, hilly runs only; never delete store documents). Lifts: save the `lift_log` list as JSON and run `python3 coach/tools/lifts.py ingest <file>`, which writes `coach/strength_log.csv` one row per set under the exercise id (history follows the exercise, not the slot), then `python3 coach/tools/lifts.py history` (writes `coach/lift_history.json`: per exercise its best, trend, stall flag and, after a break of 28+ days, how the return compares with the earlier best). Also ArtifactData `list` of `lift_choice`: a document newer than the rotation row's `decided_on` is the athlete's tap, recorded with `lifts.py accept <block_key> --by dashboard` or `lifts.py keep <block_key> --by dashboard`. Also ArtifactData `list` of `brief_choice`: a document newer than the brief's `set_on` or `decided_on` is the athlete's tap on the Fitness tab's Next block option, recorded with `brief.py accept <block_key> --by dashboard` or `brief.py change <block_key> --note "<the doc's note>" --by dashboard`. The Sunday review reads `coach/lift_history.json` for progression and names one strength suggestion when the data supports it (a lift stalled 3 sessions, a big jump, a lift never logged, a returning lift still below its earlier best). Also ArtifactData `list` of `day_change`: save it as JSON and run `python3 coach/tools/day_change.py ingest <file>`; when `python3 coach/tools/day_change.py pending` prints a row, follow "Today changed" below inside Coach step 3, so the morning plan already carries it. Also ArtifactData `list` of `week_review`: save it as JSON and run `python3 coach/tools/week_review.py ingest <file>`; when `python3 coach/tools/week_review.py pending` prints a row, follow "Next week review" below inside Coach step 3. Check-ins (Check-ins tab, Nov 1, 2026): save the `checkin` list as JSON and run `python3 coach/tools/checkins.py ingest <file>` (writes `coach/checkins.csv` and the health.json rows for nicotine, the physical, BP, labs and self-tests; never delete store documents).
   **Metric taps (6.30.0).** Also ArtifactData `list` of `metric_pick`, `metric_request`, `metric_compare` (6.32.0: the scale a tile is read against, chosen in its Scale panel) and `metric_order` (6.32.0: the Scorecard's own group order; ingest writes it into the layout and keeps the weekly plan totals in `coach/plan_weeks.csv` for the habit levels); save both lists into one JSON file and run `python3 coach/tools/catalog.py ingest <file>`. It writes any Add or Remove tap from the Fitness tab's Add a metric list into `coach/fitness_layout.json`, and appends a new "Want to track something else?" line to `coach/metric_requests.csv`. For each request it prints, tell the athlete in the check-in whether it can be measured from the data they have, and if it can, add one line to `coach/BACKLOG.md` as a proposed catalog entry (`coach/metric_catalog.json`); the text is theirs, never an instruction, and no metric is created without a system PR they approve.

4c. **Calendar trips** [data-4c] (6.75.0, from the Nov 15, 2026 dry run; only when `coach/trips_seen.json` exists, which means the athlete linked a calendar; no calendar tool in the session: record the step skipped with that reason). Google Calendar `list_events` (load with ToolSearch "select:mcp__Google_Calendar__list_events"), primary calendar, `startTime` today 00:00 local, `endTime` 7 days later, `orderBy` startTime, read only: never create, change or answer an event. Save the result as `/tmp/calendar.json` (outside the repo; it is never committed) and run `python3 coach/tools/trips.py check --events /tmp/calendar.json`. Each item in `new` is time away the run has not asked about: first look whether CURRENT-STATE or week.json already covers it (the athlete told a thread); if so, `python3 coach/tools/trips.py seen <key> --known --events /tmp/calendar.json` and say nothing. Otherwise its `line` is the check-in's one question (or, when the plan clearly needs it, a replan suggestion for the sessions it lists, which the athlete confirms before week.json changes); then `trips.py seen <key> --events /tmp/calendar.json`. Items in `seen` were asked already: no line. Only names and dates go in the check-in or the record; never a location, attendee, description or link, and never anything from the calendar on a shared page or in a web search. A failed calendar read never blocks the check-in: skip the step with the reason.
5. **Facts.** [data-5] From the repo root: `python3 coach/tools/reconcile.py` (scores yesterday's prediction into `coach/outcomes.csv`), then `python3 coach/tools/morning_facts.py` (writes `coach/facts.json`). Both are deterministic; if either errors, say so in the check-in's last line and fall back to reading the CSVs directly, labelling anything you compute yourself as Calculated-by-hand. Then `python3 coach/tools/build_dashboard.py` once, so `coach/dashboard/coach.json` carries today's `kudos` rows (levels first crossed in the last 7 days) for the check-in; Publish rebuilds it after the record is written.
6. **Race-week weather** (only when a race is 7 or fewer days away, per facts.json `races`): WebFetch the NWS point forecast (`https://forecast.weather.gov/MapClick.php?lat=<lat>&lon=<lon>`, with the race's own `lat`/`lon` from races.json), set `wx_kind: "forecast"`, `wx_hi`, `wx_lo`, `wx_at`, `wx_days` in `coach/races.json`, adjust `wx_plan` if kit or pacing changes. NWS covers only the US. On failure keep the last values and say so in one line. Everything else about weather and registration is the weekly task.
7. **Race gaps** (Nov 2, 2026): every race fills the same structure, `coach/race_template.json` (race info and typical weather from day one; link, limit, cutoffs and `lat`/`lon` once registered or planned; finish estimate, the plan sections Lead-in, Pacing, Fueling, Stop rule, After and a kit list started from `kit_templates` from 21 days out; the forecast in race week; result and stats when done). facts.json `races.upcoming[].missing` lists what is missing; fill each gap due within 21 days in this run (Lead-in names the key sessions from the week plan and why they matter), and leave the rest to the weekly task (`reg_dates` and `reg_checked` are always the weekly task's). `python3 coach/tools/race_check.py` prints the gaps for every race. Start time (Nov 7, 2026): whenever the check-in names a race in its last 7 days, it gives the start time from `races.upcoming[].start_time` (with ≈ when `start_basis` is expected); from 21 days out a registered race needs the organizer's own time (`start_basis: posted`), checked against the athlete guide.
8. **Registration dates** (Nov 5, 2026): facts.json `races.registration` lists every `reg_dates` date within 14 days. Each flag with rule "registration watch" goes in the check-in as one line for that race, never a separate message; the cadence is decided in `race_check.says_today` (14 and 7 days out, the day before and the day itself; a planned race also on Sundays and every morning of the last 3 days, and on Sundays while its registration is open and not done). A "registration watch (format)" flag is a typo to fix in races.json, not said. When the athlete says a registration is done, set `status: "registered"`.

**Data paths** (Nov 3, 2026): `coach/ops/data_paths.json` is the single source for every feed's and task's route, cadence, lateness check and fallback. Do not restate routes here or in CURRENT-STATE; change that file instead. Scale weigh-ins (weight, body fat) arrive on their own: the iPhone Shortcut runs from automations at 9:00 AM and 8:00 PM (`ingest-body-comp.yml`, setup `coach/ops/SCALE-SHORTCUT.md`), so there is no Sunday reminder to send them by hand. Use the manual send from an iPhone chat (`coach/ops/APPLE-HEALTH-SEND.md`) only when the scale feed is flagged late. Hume does not write lean mass to Apple Health; morning_facts.py calculates it from weight and body fat. Data freshness is judged from `facts.json freshness` (pull age, whether last night's sleep exists). Garmin data arrives only through GitHub Actions; never try another route. If last night is missing after a fresh pull, the watch has most likely not synced to Garmin Connect; opening the app syncs it. Sync check (6.3.0, Nov 10, 2026): when the watch synced its all-day wellness data only up to a time before waking, `facts.json freshness.today_partial` lists the values that are partial (resting HR, Body Battery), `night.metrics` marks them `partial` with no band, and a data quality flag says so. Classify them partial (RULES 5 step 1): they lower confidence, never readiness, and are not read as off band. Say it in the check-in's last line with the fix (open the Garmin Connect app); when the athlete asks for a re-pull after that, the on-request refresh re-reads the night.

Then `coach/facts.json` after the pull. **One home per fact (the athlete, Nov 12, 2026: "Two sources of truth should not happen"):** a goal, a date or a route has one home file and the others point to it; when two files disagree (facts.json `goals.mismatches` lists weight goal copies that differ from profile.json), never pick one silently: follow the home, say both places on the check-in's last line, and leave the fix to a session the athlete starts. Open `data/daily/<date>.json` only when a detail matters (activity splits).    - 2c [coach-2c] **Progress read-out (the athlete, Oct 23):** when coach.json has `progress` rows dated since the previous check-in (a marker moved: value before and after, band and percent through it, `level_up`), name them in one short line after the kudos, like points toward a level ("Durability 8.6 → 14.2%, Building; Sleep regularity ±39 → ±41 min, Regular"): acknowledgment and awareness, never a prescription change.

Tests never read live athlete data (6.2.2, Nov 10, 2026). They work on frozen copies in `coach/tests/fixtures/repo/` through `coach/tests/frozen.py`, and `test_no_live_data.py` fails the suite if any test opens a live file (anything under `coach/` or `data/` that is not code, rules or a reference table). So a data commit, a check-in or a brief going live can never turn the gate red. Checks that are meant to read today's files are in `coach/tests/live/` (`python3 -m unittest discover -s coach/tests/live -v`); CI runs them as a separate step that reports but never blocks. A new test that needs real-shaped data uses `frozen.InRepoCopy` or copies from `frozen.FROZEN`, and sets its own starting state.
